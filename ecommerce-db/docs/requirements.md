# Вимоги до системи «Електронна комерція з кількома магазинами»

Платформа-маркетплейс: кілька незалежних магазинів продають товари зі спільного каталогу;
покупець має один акаунт і може купувати в будь-якому магазині.

## Функціональні вимоги та сутності, що з них випливають

| № | Вимога | Сутності |
|---|--------|----------|
| FR1 | Реєстрація користувачів; ролі: адміністратор, власник магазину, працівник, покупець | `users`, `roles`, `user_roles` |
| FR2 | Покупець зберігає кілька адрес доставки | `addresses` |
| FR3 | Платформа підтримує багато магазинів; у магазині є власник і працівники | `stores`, `store_staff` |
| FR4 | Єдиний каталог товарів із категоріями (дерево), брендами та довільними атрибутами | `categories`, `brands`, `products` |
| FR5 | Той самий товар продається в різних магазинах з різною ціною та власним залишком | `store_products` (зв'язок M:N) |
| FR6 | Кошик покупця окремий для кожного магазину | `carts`, `cart_items` |
| FR7 | Промокоди: глобальні або лише для одного магазину; відсоток або фіксована сума; ліміти використання та строк | `coupons` |
| FR8 | Кожен магазин має власні способи доставки | `shipping_methods` |
| FR9 | Оформлення замовлення з кошика: фіксація цін на момент покупки, списання залишків, знижка за промокодом | `orders`, `order_items` |
| FR10 | Життєвий цикл замовлення (pending → paid → processing → shipped → delivered; cancelled / refunded) та його історія | `orders.status`, `order_status_history` |
| FR11 | Оплата замовлення та відстеження відправлення | `payments`, `shipments` |
| FR12 | Відгуки та оцінки лише від покупців, які отримали товар | `reviews` |
| FR13 | Облік рухів складу (поповнення, продаж, скасування) | `inventory_movements` |
| FR14 | Журнал змін ключових даних | `audit_log` |

## Нефункціональні вимоги

| № | Вимога | Реалізація |
|---|--------|------------|
| NFR1 | **Soft delete**: користувачі, магазини, категорії, товари, пропозиції магазинів, промокоди та відгуки не видаляються фізично (історія замовлень посилається на них) | `is_deleted`, `deleted_at`, `deleted_by`; тригер `trg_prevent_hard_delete`; часткові унікальні індекси (`email`, `sku`, `code` можна використати знову) |
| NFR2 | **Аудит**: для змінюваних сутностей зберігати дату останньої зміни та користувача, що змінив | `updated_at`, `updated_by`; тригер `trg_set_audit_columns`; актор передається процедурою `sp_set_actor` |
| NFR3 | Цілісність замовлень: суми завжди відповідають позиціям, статуси змінюються лише за дозволеною схемою, скасування повертає товар на склад | тригери `trg_recalc_order_totals`, `trg_validate_order_status`, `trg_restock_on_cancel` |
| NFR4 | Усі зміни даних із застосунку — лише через збережені процедури, читання — лише через розрізи (views) | схема `shop`, файли `04_views.sql`, `05_procedures.sql`; шар Repository + Unit of Work |
| NFR5 | Швидкий пошук товарів і звіти на великих обсягах | індекси B-tree (часткові, складені, покривні), GIN, BRIN, HASH |

## Бізнес-правила

1. Кошик не може містити більше одиниць товару, ніж є на складі.
2. Замовлення належить одному магазину; доставка та промокод мають відповідати цьому магазину.
3. Оплата приймається лише за точною сумою замовлення зі статусом `pending`.
4. Скасувати можна замовлення зі статусом pending / paid / processing — товар повертається на склад, використання промокоду зменшується, оплата позначається як повернена.
5. Відгук на товар може залишити лише покупець із замовленням у статусі `delivered`; один активний відгук на товар.
6. Email, SKU, slug та код промокоду унікальні серед не видалених записів.
